## 5.1 权重要一份，cache 要 N 份

先纠正一个大多数人（包括学了 Week 2 的你）脑中的默认图景：
"推理占内存 = 模型权重占内存。"

对训练来说这图景大致对。但对**推理服务**来说，真正的大户另有其人。
把两类内存摆在一起对比（以 Qwen3-0.6B、bf16 为例）：

| | 模型权重 | KV cache |
|---|---|---|
| 大小 | 约 1.2 GB（6 亿参数 × 2 字节） | 每 token 112 KB，**随序列变长线性增长** |
| 份数 | 全服务**共享一份** | **每个请求一份**，互不共享 |
| 生命周期 | 加载一次，雷打不动 | 请求来则生，请求走则灭 |

单个看 cache 不大——一段 4096 token 的对话才 448 MB。但推理服务赚的是
**并发**的钱：32 个人同时聊天，每人 4096 token，cache 就是 14 GB，
**十倍于权重**。模型再大一号（比如 7B、70B），权重和 cache 一起按比例涨，
但 cache 还要额外乘以并发数。

于是得到一个推理引擎的核心结论：

> 📌 **划重点：** 决定一台机器**能同时服务多少个请求**的，不是算力，
> 而是 KV cache 装不装得下。**内存 = 并发数 = 吞吐 = 钱。**

## 5.2 一道容量规划题

把上一章的算账能力用起来，解一道真实的工程题：

> 一张 24 GB 显存的卡，跑 Qwen3-0.6B（权重约 1.2 GB），每个请求平均
> 2048 token。最多同时服务多少请求？

心算：

1. 可用于 cache 的显存：$24 - 1.2 \approx 22.8$ GB（先忽略框架自身开销）；
2. 每个请求：$2048 \times 112\ \text{KB} = 224$ MB；
3. $22.8\ \text{GB} \div 224\ \text{MB} \approx 100$ 个请求。

也就是说：这张卡的瓶颈**不是**"算不动 100 个人"，而是"装不下第 101 个人的档案"。
想让并发翻倍？要么砍每个请求占的内存，要么把同样的内存利用得更干净——
这正是下面三条路。

## 5.3 省内存的三条主路（本周先看地图）

工业界围着 KV cache 省内存的努力，大致三条路线。本周你只要知道"各自砍的是
公式的哪一项"，后面几周都会亲手做到：

**路线一：GQA——砍头数（Week 6）。** 标准多头注意力里 Q、K、V 头数一样多。
GQA（分组查询注意力）让多个 Q 头**共享**一对 K/V 头。Qwen3-0.6B 就是
16 个 Q 头配 8 个 KV 头——cache 直接省一半。上一章的公式里那个
`num_heads = 8`，已经是 GQA 打过折的价格了。更激进的 MQA 只留 1 对 KV 头，
省 16 倍。

**路线二：分页——砍浪费（Week 4，本课程的看家菜）。** 我们的 `NaiveKVCache`
有两个隐藏浪费：① 每条序列要**连续**的一大块内存，碎掉的空隙用不起来
（像停车场要求每辆车横着占三个连号车位）；② 为防序列变长，得**按最大长度
预留**，实际只聊了三句话的请求也占着 4096 的坑。PagedAttention 把 cache 切成
固定大小的"块"，用块表做逻辑→物理映射——操作系统虚拟内存的思想，原样搬进
推理引擎。这是 vLLM 的成名绝技。

**路线三：量化——砍字节数。** 公式里的 `dtype_bytes` 从 2 字节（bf16）压到
1 字节（int8）甚至更低，cache 直接减半再减半，代价是微小的精度损失。
本课程不展开，但你已经会算账了：砍的就是最后一项。

> 💡 **你可能会问：为什么不干脆限制最大序列长度，一刀切？**
>
> 可以，而且大家都设上限（比如 4096）。但**平均**长度远小于上限：大多数请求
> 只聊几百 token，你却按上限给它预留了内存——这就是路线二要消灭的
> "预留浪费"。一刀切只防住了最坏情况，没治好日常浪费。

## 5.4 本周在 8 周地图上的位置

回头看一眼我们走过的路，和前面的路：

| 周 | 解决的问题 | 状态 |
|---|---|---|
| W1 | 词是怎么一个词一个词蹦出来的（自回归） | ✅ |
| W2 | 引擎的心脏：手写 Transformer | ✅ |
| **W3** | **别重复算已经算过的：KV cache** | ✅ 本周 |
| W4 | cache 的内存碎片与预留浪费：分页（PagedAttention） | ⬅️ 下一站 |
| W5 | 多个请求怎么挤在一起跑：continuous batching | |
| W6 | 采样 + 加载真实 Qwen3 权重（GQA 在这里） | |
| W7–8 | 引擎化、对标真实 vLLM 源码 | |

注意这个递进的逻辑链：**W3 发明了 cache，W4 给 cache 治内存病，W5 让很多请求
共用治病后的 cache。** vLLM 论文的核心贡献（PagedAttention + continuous batching）
就是这条链的后两环——而它们存在的全部理由，都是本周这个看似朴素的想法：
"算过的存下来。"

> 📌 **对标 vLLM：** 真实 vLLM 里，KV cache 的内存管理集中在这几个文件：
> `vllm/v1/core/kv_cache_manager.py`（给请求分配/回收块）、
> `vllm/v1/core/block_pool.py`（块的大管家）、
> `vllm/model_executor/layers/attention/attention.py`（注意力层读写 cache 的接口）。
> Week 8 我们会打开它们——而到那时，这些文件里的每个核心概念你都亲手写过。

## 5.5 一句话带走

本周你只写了不到 50 行代码（`append_and_get` + `generate_with_cache` +
一处位置偏移 + 一个算账函数），但你已经摸到了 LLM 推理优化的总开关：

- **时间**上：不重复计算，每步只算新词（prefill / decode 两段式）；
- **空间**上：每 token 112 KB 的内存账，决定了服务的并发上限；
- **工程**上：省下的每一字节 cache，都直接换成更多的同时在线用户。

下周我们去治 `torch.cat` 留下的病：反复搬家、连续分配、按最大长度预留。
你会看到操作系统里"分页"这个几十年前的智慧，如何原封不动地变成
vLLM 的招牌——PagedAttention。
