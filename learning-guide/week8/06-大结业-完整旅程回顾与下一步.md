## 6.1 八周地图：八个问题，八根刺

把 8 周压缩成一张表。每一周都在回答一个问题、拔掉一根刺：

| 周 | 问题 | 我们的答案 | 拔掉之后浮现的新问题 |
|---|---|---|---|
| W1 | 词是怎么一个个蹦出来的？ | 自回归：预测下一个词，接回输入再来 | 每步整段重算，太浪费 |
| W2 | 模型内部在干什么？ | 手写 mini Transformer：注意力、多头、残差 | 老词的 K/V 每步重算 |
| W3 | 怎么不重复算？ | KV cache：存 K/V 不存 Q，prefill/decode 两阶段 | 连续存储 + cat 搬家，内存碎 |
| W4 | 内存怎么不浪费？ | 分页：BlockPool 发块、BlockTable 记账、PagedKVCache 存取 | 请求多了怎么调度？ |
| W5 | 一堆请求怎么一起跑？ | continuous batching：waiting/running 队列、每步点名 | 生成全是一个调，怎么花样采样？ |
| W6 | 怎么让引擎说人话、说真话？ | 温度/top-k/top-p 采样；加载 Qwen3 真实权重 | 脚本不能当服务用 |
| W7 | 怎么从脚本变成引擎？ | LLMEngine 的 `step()` 心跳、generate/stream、LLM 门面 | 我们离真家伙还差多远？ |
| W8 | 离真家伙多远？ | 模块对照、带读源码、实测：约四成功力，差距逐条指认 | （你的下一步，见 6.3） |

注意这张表的"链条结构"：**每一周的答案，都立刻暴露下一周的问题。**
这不是巧合，这正是 vLLM 这个项目的真实演化史——PagedAttention 论文解决
内存（我们的 W4），continuous batching（Orca 系统的思想，我们的 W5）解决吞吐，
后面的 chunked prefill、prefix caching、投机采样……全是同一根链条上的
下一环。你亲手把链条的前七环打了一遍。

## 6.2 结业目标自查

开课时说好的三条结业目标，逐条对一下：

**① 能手写加载 Qwen3-0.6B 真实权重的推理引擎（分页 KV cache +
continuous batching + 采样 + 流式输出），并说出每个模块在解决什么问题。**

自测方法：合上所有资料，能画出这张图吗——
`LLM`（门面）→ `LLMEngine.step()`（点名→prefill/decode→采样→登记）→
`Scheduler`（两个队列）→ `BlockPool/BlockTable`（页表）→
`PagedKVCache`（仓库）→ `Qwen3ForCausalLM`（模型）→ `Sampler`（采样）。
每个模块能不能说出"没有它会怎样"？能，这条就过了。

**② 能打开真实 vllm v1 的 `scheduler.py` / `block_pool.py` / `llm_engine.py`
不慌，认得出每个核心概念。**

本周第 1、2 章做的就是这件事。自测方法：随便打开
`.venv` 里的 `vllm/v1/core/sched/scheduler.py`，
找到 `token_budget`、`self.waiting`、`self.running`、`allocate_slots`，
能不能各自说出对应我们写过的什么？

**③ 讲得清 PagedAttention 和 continuous batching 各自解决了什么浪费。**

一句话版本，拿去直接用：

- **PagedAttention**：把 KV cache 切成固定大小的块 + 页表映射，
  消灭"连续预留"造成的内存碎片——**省内存，省出来的内存换成更多并发**；
- **continuous batching**：请求随来随走、每步重新点名组批，
  消灭"静态批处理里短请求陪长请求空跑"的浪费——**把 GPU 的每一步都塞满**。

三条都打勾了？**恭喜，你毕业了。**

## 6.3 下一步：四条路，按兴趣选

毕业不是终点。你面前有四条路，难度和收获各不相同：

### 路线 A：把 minivllm 继续做完（最推荐）

在第 3 章的三个高级特性里挑一个，亲手加进 minivllm：

- **chunked prefill**（中等难度）：给 `schedule()` 加 token 预算，
  模型的 `prefill` 支持"从中间位置继续算"。改完用第 4 章的工具测：
  长 prompt 下其他请求的 TTFT 应该明显改善；
- **prefix caching**（中高难度）：`BlockPool` 加哈希字典和引用计数，
  `Scheduler` 准入前查 `get_computed_blocks`。改完写个测试：
  两个相同开头的请求，第二个的 prefill 应该跳过共享部分；
- **先做哪个？** 建议 chunked prefill——它的公式你已经在真实
  `schedule()` 里读过了（第 2 章 2.4 节）。

### 路线 B：投机采样（speculative decoding）

思想一句话：**用小模型先"猜"几个词，大模型一次前向批量验算**，
猜对的直接收，猜错的回退。把大模型的"一个词一次前向"变成
"几个词一次前向"，单请求延迟直接打折。真实 vLLM 里看
`vllm/v1/spec_decode/`——有了本课程的底子，你能认出它的草稿 token
就是 `schedule()` 注释里的 `spec_token_ids`。

### 路线 C：量化与更小的模型

把 bfloat16 的权重压成 8 bit、4 bit（AWQ/GPTQ），内存减半、
带宽减半、速度上升。你会真正理解"推理是带宽受限"这句话——
Week 3 的内存账单会再次派上用场。

### 路线 D：多卡与工程化

张量并行（一层切几张卡）、流水线并行（几层放一张卡）、
`AsyncLLMEngine` 与 API server（`vllm/entrypoints/`）。
这条路通向"生产级部署"，适合想往推理引擎工程方向走的你。

四条路没有先后，但**共同的地基你都已经有了**：
不管选哪条，第一步都是打开真实源码——而这正是你本周刚练过的肌肉。

## 6.4 致谢与最后一句话

谢谢你把 8 周走完。这门课写的时候只有一个信念：

> **推理引擎不是魔法。它是一串"这有什么浪费 → 怎么省"的朴素问答，**
> **每个答案都不超过一页纸，难的是有人带你按正确的顺序问。**

现在你不仅知道答案，还知道问题是怎么一个个冒出来的。
下次再看到某个推理框架宣布"吞吐提升 40%"，你的第一反应不会是
"好厉害"，而是"它省了哪一笔？kernel？调度？还是缓存？"——

**这就是这 8 周送你的东西：一双看得见浪费的眼睛。**

毕业快乐。🎓
