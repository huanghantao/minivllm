## 2.1 问题：一次算整段，就会"剧透"

上一章的注意力是对**整段话**一起算的：$L \times L$ 的分数表里，每个词都会和所有词
比对——包括**排在它后面的词**。

这在生成时是绝对不能发生的。想象模型正在写小说，写到第 3 个词时，第 4、5、6 个词
**根本还不存在**。如果第 3 个词的计算用到了第 5 个词的信息，那就等于考试偷看了
后面的答案——整个"一个词一个词往外蹦"的游戏规则就被破坏了。

GPT、Qwen 就是这样生成文本的：只根据已有的 token，一次预测一个新 token。
这叫**自回归生成**，它们采用的模型结构通常称为 **decoder-only**。因果掩码
正是这种结构用来保证"只看历史"的关键机制。不过，为什么它叫 decoder-only？
这得从 Transformer 最初的样子说起。

### 2.1.1 从 encoder–decoder 到 decoder-only

`decoder-only` 不是说"模型只会做解码"，这个名字来自原始 Transformer 的
**encoder–decoder（编码器–解码器）结构**。2017 年的 Transformer 最初面向翻译一类
"读一段，再写一段"的任务：

```text
源文（待翻译的句子） → Encoder → 整句的表示
                                      ↓ cross-attention
目标文前缀             → Decoder → 下一个目标词
```

- **Encoder** 的任务是"读懂原文"。原文在计算开始时已经全部存在，所以每个词
  可以同时看左边和右边，不需要因果掩码。
- **Decoder** 的任务是"从左到右写译文"。它先对已写出的目标文做带因果掩码的
  self-attention，再通过 cross-attention 去读 Encoder 的输出。

到了 GPT 这类**自回归语言模型**，任务变成了"给定同一段文本的前缀，预测它的
下一个 token"。此时没有一段需要单独编码的源文：前面的 token 本身就是上下文。
因此可以：

1. 删掉整个 Encoder；
2. 删掉 Decoder 中专门读 Encoder 输出的 cross-attention；
3. 保留带因果掩码的 self-attention，反复堆叠，每个位置预测下一个 token。

这就是 **decoder-only**。严格来说，它不是把原始 Decoder 一字不改地拆下来，
而是沿用了 Decoder 的"因果 self-attention + 逐词预测"思路，同时去掉了对 Encoder
的依赖。所以，**decoder-only 这个名字描述的是模型结构，因果掩码才是它
"不许偷看未来"的具体机制。**

> 📌 **对标 vLLM：** 现在主流生成式 LLM 大多采用 decoder-only 结构（GPT 家族、
> Qwen 家族都是）。真实 vLLM 的 `vllm/model_executor/models/qwen3.py` 里，
> `Qwen3Attention` 创建时带着 `attn_type=AttentionType.DECODER`，
> 就是在声明"我是因果的，底层 kernel 请自觉挡住未来"。

名字理清了，现在回到这类模型必须遵守的规矩：

> **第 i 个词，只允许看位置 ≤ i 的词（包括自己）。**

## 2.2 办法：把不许看的位置打成负无穷

怎么执行这条规矩？上一章埋的钩子揭晓：在 softmax **之前**，把分数表里"未来"的格子
填成 $-\infty$。

为什么是 $-\infty$？看 softmax 的公式就明白了：

$$
\text{softmax}(s_i) = \frac{e^{s_i}}{\sum_j e^{s_j}}
$$

$e^{-\infty} = 0$——被填 $-\infty$ 的位置，softmax 之后权重**恰好是 0**，兑内容时
一滴都兑不进来。而且总和还是 1（$-\infty$ 不影响分母里其他项）。干净利落。

所以我们需要一张表格，告诉 `masked_fill` 哪些位置允许看、哪些不许。这张表就是
**因果掩码（causal mask）**。

## 2.3 make_causal_mask：一张"谁可以看谁"的表

约定（和 reference 一致，别搞反）：**True = 允许看，False = 禁止**。

`make_causal_mask(3)` 生成 3 个词的因果掩码，长这样（行 = 查询词，列 = 被看的词）：

| 查询＼被看 | 词 0 | 词 1 | 词 2 |
|---|---|---|---|
| **词 0** | True | False | False |
| **词 1** | True | True | False |
| **词 2** | True | True | True |

一个"下三角全 True"的方阵：词 0 只能看自己；词 1 能看 0 和自己；词 2 全都能看。
右上角那片 False，就是"未来"。

reference 的实现只有四行，但值得逐行看：

```python
def make_causal_mask(q_len, kv_len=None):
    if kv_len is None:
        kv_len = q_len
    offset = kv_len - q_len  # 前面这 offset 个是缓存的旧词，全部允许看
    i = torch.arange(q_len).unsqueeze(1)  # 查询在"本次新词"里的下标
    j = torch.arange(kv_len).unsqueeze(0)  # 键在全部序列里的下标
    return j <= i + offset
```

- `torch.arange(n)`：生成 `[0, 1, ..., n-1]`，就是"下标列表"；
- `.unsqueeze(1)`：在最后加一维——`i` 从 `(q_len,)` 变成 `(q_len, 1)`（竖过来）；
  `j` 变成 `(1, kv_len)`（横着放）；
- `j <= i + offset`：一竖一横做比较，PyTorch 会**广播**成 `(q_len, kv_len)` 的表格，
  每个格子回答"第 j 个键的位置 ≤ 第 i 个查询的位置吗"。

先别管 `offset`，2.5 节专门讲它。`q_len == kv_len` 时 `offset = 0`，条件就是
`j <= i`：列下标不超过行下标——正好画出上面那张下三角表。

## 2.4 手算 2×2：被挡的位置真的变成 0

用 `tests/test_w2.py` 里 `test_sdpa_mask_blocks_future` 的设定，我们手算一遍。
两个词，Q 和 K 全是 1（每个向量 4 个 1），所以任何两个词的点积都是 4，
除以 $\sqrt{4}=2$，**所有分数都是 2**——完全中性，方便我们看掩码的纯效果。
V 故意取成一眼能认出来的：词 0 的 V 是 `[1, 0, 0, 0]`，词 1 的 V 是 `[0, 0, 0, 2]`。

**不加掩码时**：每个查询的两个分数都是 `[2, 2]`，softmax 后是 `[0.5, 0.5]`，
输出 = $0.5 \times [1,0,0,0] + 0.5 \times [0,0,0,2] = [0.5, 0, 0, 1]$。

**加上 `make_causal_mask(2)` 之后**，掩码是：

| 查询＼被看 | 词 0 | 词 1 |
|---|---|---|
| **词 0** | True | False |
| **词 1** | True | True |

- 词 0 的分数变成 `[2, -∞]` → softmax 得 `[1, 0]` → 输出 =
  $1 \times [1,0,0,0] + 0 \times [0,0,0,2] = [1, 0, 0, 0]$。**词 1 的内容一点没漏进来**；
- 词 1 的分数不变 `[2, 2]` → `[0.5, 0.5]` → 输出 `[0.5, 0, 0, 1]`，两个词都能看到。

测试里断言的正是这件事：`weights[0, 0, 0, 1] == 0.0`（词 0 看词 1 的权重是 0），
而 `weights[0, 0, 1, 1] > 0.0`（词 1 看词 1 畅通）。

![真实注意力权重热力图：上三角被打上 ✕，表示被因果掩码禁止](../../figures/out/w2_attention_heatmap.png)

这张图不是示意图，是**用我们课程的 MiniTransformer（reference 实现）真实跑出来的**
注意力权重：6 个词"我 爱 吃 苹 果 。"、4 个头。注意每个头的右上角全是 ✕——
那就是被掩码打成 $-\infty$、权重归零的"未来区域"；左下角颜色深浅不一，
就是 softmax 之后各词真实分到的注意力。（这是随机初始化的权重，所以分布没什么
语义规律——Week 6 加载真实权重后，这些图才会"说话"。）

## 2.5 q_len ≠ kv_len：给 KV cache 埋的伏笔

到目前为止，查询和键一样多（方阵）。但 `make_causal_mask` 还接受第二个参数
`kv_len`，允许 **q_len < kv_len**。什么时候会这样？

剧透一点 Week 3：生成第 100 个词时，前 99 个词的 K/V 其实**已经算过了**，完全可以
存下来（这就是 KV cache），不用重算。那时每次前向只有 1 个新查询（q_len = 1），
但要对着 100 个键（kv_len = 100）打分。

规则很简单：**缓存的旧词全部允许看，新词之间遵守因果。** 比如 `make_causal_mask(2, 4)`
——2 个新词 + 2 个旧词（这正是测试 `test_causal_mask_with_cache` 的场景）：

| 查询＼被看 | 旧词 0 | 旧词 1 | 新词 0 | 新词 1 |
|---|---|---|---|---|
| **新词 0** | True | True | True | False |
| **新词 1** | True | True | True | True |

这就是 `offset = kv_len - q_len` 的作用：新词 0 在"全部序列"里的真实位置是
`0 + offset = 2`，所以条件 `j <= i + offset` 放行了前两列旧词和它自己。
现在你只需要记住"这个参数是为下周准备的"，到时候会一拍大腿。

> 💡 **你可能会问：为什么不让掩码直接是 0/1 的浮点数，加到分数上？**
>
> 可以，很多实现确实用"加 $-\infty$ 的浮点掩码"。我们选 **BoolTensor + True=允许**，
> 因为"这张表在回答一个是否问题"，布尔语义最直白，而且 Week 4 批量 decode 时的
> 填充掩码（pad mask）也是同样的 True=允许约定，全课程统一。

> ⚠️ **易踩坑：**
>
> - **True/False 语义写反**是最常见的 bug：我们的约定是 True=允许看，
>   `masked_fill` 里填的是 `~mask`（取反后才是"要挡的位置"）；
> - 掩码在 CPU 上生成、模型在 MPS 上跑时，别忘了 `.to(x.device)` 搬过去
>   （第 3 章的 `MultiHeadAttention.forward` 里你会看到这一步）；
> - `make_causal_mask` 返回的是 `(q_len, kv_len)` 的**二维**表，喂给
>   `(B, H, L, L)` 的分数时靠 PyTorch 广播自动对齐，不用手动扩维度。

> 📌 **划重点：** 因果掩码 = 一张下三角 Boolean 表（True=允许看）；执行手段是
> 把被禁位置的分数填成 $-\infty$，softmax 自动把它们归零。`kv_len > q_len` 的情形
> 是为 KV cache 准备的，下周见分晓。
