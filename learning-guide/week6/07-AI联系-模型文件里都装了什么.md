## 7.1 打开模型目录

对拍测试通过 `snapshot_download` 下载的 Qwen3-0.6B，目录里一共 7 个文件
（在 HuggingFace 的默认缓存目录 `~/.cache/huggingface/hub/models--Qwen--Qwen3-0.6B/snapshots/`
下——这是标准位置，大家机器上都在这里，你也可以亲手打开看看）：

| 文件 | 大小量级 | 管什么 |
|---|---|---|
| `config.json` | 1 KB | 模型身份证：身材数据（层数、头数、维度……） |
| `model.safetensors` | 1.4 GB | **权重本体**：311 个张量、约 7.5 亿个参数 |
| `tokenizer.json` | 几 MB | 分词器打包版：词表 + BPE 规则 + 特殊符号 |
| `vocab.json` | 几 MB | 词 → id 的字典（分词器的原料） |
| `merges.txt` | 几 MB | BPE 合并规则（分词器的原料） |
| `tokenizer_config.json` | 几 KB | 分词器设置（特殊 token、聊天模板等） |
| `generation_config.json` | 1 KB | 官方推荐的**采样默认值** |

一个模型 = **架构描述（config）+ 权重（safetensors）+ 分词器（三个文件）+ 生成默认值**。前两个我们本周已经用上了；分词器是 Week 7 的主角之一
（把字符串变成 token id 再变回来）；最后一个下面细说。

## 7.2 config.json：模型的身份证

第 6 章的 `Qwen3Config` 读的就是它。把关键字段挑出来对照着看，
现在每一个你都认识了：

```json
{
  "hidden_size": 1024,
  "num_hidden_layers": 28,
  "num_attention_heads": 16,
  "num_key_value_heads": 8,
  "head_dim": 128,
  "intermediate_size": 3072,
  "vocab_size": 151936,
  "rope_theta": 1000000,
  "rms_norm_eps": 1e-06,
  "max_position_embeddings": 40960,
  "tie_word_embeddings": true,
  "eos_token_id": 151645
}
```

- `num_key_value_heads: 8` < `num_attention_heads: 16` —— GQA，第 5 章；
- `rope_theta: 1000000` —— RoPE 的转速基数 base，第 5 章；
- `rms_norm_eps` —— RMSNorm 的保险丝 $\epsilon$，第 4 章；
- `max_position_embeddings: 40960` —— 训练时见过的最长序列
  （RoPE 不用"背"位置，这个上限比查表法宽松得多）；
- `tie_word_embeddings` —— 7.4 节细讲；
- `eos_token_id: 151645` —— 结束符 `<|im_end|>` 的 id。
  引擎解码时遇到它就该收工（Week 7 会真正用上）。

看，这份身份证上已经没有陌生的词了——这就是本周的收获。

## 7.3 safetensors：一个"名字 → 张量"的大字典

1.4 GB 的 `model.safetensors` 是全部身价的所在。它的格式朴素得可爱：

> 文件开头一个 JSON 目录（每个张量的名字、形状、dtype、在文件里的偏移），
> 后面跟着所有张量的原始字节。

为什么不用 Python 自带的 pickle（`.pt` / `.bin` 老格式）？因为
**pickle 能执行任意代码**——反序列化一个恶意构造的 pickle 文件，
等于在你电脑上运行陌生人的程序。模型文件天天从网上下载，
这等于请木马进门。safetensors 里只有纯数据，没有任何可执行的东西，
而且那个"头部目录"的设计还支持**内存映射**：可以只把需要的张量
读进内存，不用一次性加载 1.4 GB（真实 vLLM 加载 70B 模型就靠这个）。

我们数过它的家底：311 个张量 = 28 层 × 每层 11 个 + 3 个全局的
（`embed_tokens.weight`、`norm.weight`、`lm_head.weight`）。
每层那 11 个，你上周全都写过对应的模块：

```
model.layers.0.self_attn.{q,k,v,o}_proj.weight   ← 4 个投影矩阵
model.layers.0.self_attn.{q,k}_norm.weight       ← QK-Norm 两个
model.layers.0.mlp.{gate,up,down}_proj.weight    ← SwiGLU 三个
model.layers.0.{input,post_attention}_layernorm.weight  ← 两个 RMSNorm
```

参数总数 751 632 384（约 7.5 亿）。等等——这模型不是叫 **0.6B** 吗？

名字是约数，拆开看：28 层躯干约 4.4 亿，嵌入矩阵
$151936 \times 1024 \approx 1.56$ 亿，输出头 lm_head 又约 1.56 亿。
"0.6B"大致说的是躯干加嵌入的量级。词表大的模型，嵌入这一对"门面"
能占到总参数的三四成——这也是下一个话题存在的理由。

## 7.4 tie_word_embeddings：一块矩阵，两种用法

`embed_tokens` 和 `lm_head` 形状一模一样（都是 $151936 \times 1024$），
干的活却正好相反：

- **embed_tokens**：词 → 向量。第 $i$ 行是词 $i$ 的"长相"，
  前向开始时被查阅；
- **lm_head**：向量 → 词表上每个词的分数。前向结束时做一次矩阵乘，
  相当于拿隐藏向量和每一行算匹配度。

注意第二件事的读法：lm_head 的第 $i$ 行，就是"词 $i$ 该有的样子"的
**模板**——隐藏向量和它越像，词 $i$ 的分数越高。也就是说：

> 嵌入矩阵的第 $i$ 行学的是"词 $i$ 长什么样"；
> lm_head 的第 $i$ 行学的是"该输出词 $i$ 时，隐藏向量长什么样"。
> 这两份知识**本质上是同一份**——都是词 $i$ 在这个语义空间里的坐标。

既然如此，何必存两份？`tie_word_embeddings: true` 就是让 lm_head
**直接借用**嵌入矩阵（我们 `from_pretrained` 里那行
`model.lm_head.weight = model.embed_tokens.weight`）。一举省下 1.5 亿
参数——对 0.6B 的小模型来说是 20% 的体重，对小模型几乎标配；
大模型（70B 级）词表占比小，常选择不绑。

> 💡 **你可能会问：绑在一起会不会互相拖后腿？**
>
> 会有一点张力（两个岗位对这块矩阵的要求不完全一致），所以超大模型
> 倾向分开。但小模型上实测掉点很小、省参数很香——工程上又是熟悉的
> 性价比权衡，和 GQA 的故事异曲同工。

## 7.5 generation_config.json：官方给你的采样默认值

最后看一眼这个 1 KB 的小文件，本周前半的劳动成果全在里面：

```json
{
    "bos_token_id": 151643,
    "eos_token_id": [151645, 151643],
    "temperature": 0.6,
    "top_k": 20,
    "top_p": 0.95
}
```

- `temperature / top_k / top_p`：官方推荐不是贪心，而是**低温 + 双圈**——
  你第 1~3 章手写的三个函数，就是这三个数字的实现；
- `eos_token_id` 是个**列表**：`<|im_end|>`（151645，聊天轮次结束）和
  `<|endoftext|>`（151643，文档结束）都算"说完话了"。
  Week 5 的调度器见过 `finish_reason` 的 `stop`，就是让引擎遇到这些
  id 时给请求打上的标记。

> 📌 **划重点：** 一个模型目录 = 身份证（config.json）+ 权重（safetensors，
> "名字 → 张量"的纯数据字典）+ 分词器三件套 + 采样默认值
> （generation_config.json）；`tie_word_embeddings` 让输出头白嫖嵌入矩阵，
> 省 20% 参数。

## 7.6 本周在 8 周地图上的位置

| 周 | 解决的问题 | 状态 |
|---|---|---|
| W1 | 词是怎么一个词一个词蹦出来的（自回归） | ✅ |
| W2 | 引擎的心脏：手写 Transformer | ✅ |
| W3 | 别重复算已经算过的：KV cache | ✅ |
| W4 | cache 的内存碎片与预留浪费：分页 | ✅ |
| W5 | 多个请求怎么挤在一起跑：continuous batching | ✅ |
| **W6** | **采样 + 加载真实 Qwen3 权重** | ✅ 本周 |
| W7 | 从脚本到服务：LLMEngine / stream / LLM 门面 | ⬅️ 下一站 |
| W8 | 对标真实 vLLM 源码、性能测量、结业 | |

现在的库存盘点：分页 KV cache 有了，调度器有了，采样器有了，
**一个权重为真、逐词对拍通过的 Qwen3 模型**也有了。但组装方式还是
Week 5 那个"一次进一批、跑完拉倒"的函数——离一个能随时接单、
逐字往外吐的**服务**还差一层外壳。

Week 7 就造这层外壳：`LLMEngine`（引擎的心跳 `step()`）、
`generate` 与 `stream` 两种用法、以及一行起引擎的 `LLM` 门面。
到那时，你会第一次体验到"自己的引擎 + 真实的模型 + 打字机效果的输出"
——那感觉和用 ChatGPT 几乎一样，只是每一行代码都是你写的。

> 📌 **对标 vLLM：** 真实 vLLM 读 config 在
> `vllm/transformers_utils/config.py`，加载权重在
> `vllm/model_executor/model_loader/`（含 safetensors 的内存映射加载），
> 分词器包装在 `vllm/inputs/` 和 `vllm/transformers_utils/tokenizer.py`。
> 三件套的分工和我们这个目录巡礼完全一致。
