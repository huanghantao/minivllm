> 本章你将：

## 6.1 省的不是内存，是并发

第 1 章我们列过传统连续分配的三种浪费：外部碎片、内部碎片、预留浪费。分页把它们全消灭了。但"省内存"只是中间结果——**省下来的内存去了哪，才是重点**。

链条是这样的：

1. 推理时显存里最大的、最能伸缩的占用就是 KV cache（模型权重是固定的，Week 3 算过账）；
2. KV cache 的利用率从"只有两三成装上真数据"提到"几乎装满"，**同样的显存就能装下更多请求的 K/V**；
3. 同时能跑的请求多了，GPU 每一批干的活就大，**吞吐量（每秒生成的 token 数）**直接抬高；
4. 吞吐高了，平摊到每个用户身上的成本就降了。

所以 PagedAttention 论文里那句"内存利用率"的改善，落到业务上就是一句话：**同样一张卡，同时服务更多的人。** 这也是 vLLM 一出世就把吞吐拉高一个数量级、迅速成为推理引擎事实标准的原因之一。

PagedAttention 之后，业界几乎再没人用"连续分配"做在线服务了——你今天用的各种大模型 API，背后几乎都有这套分页机制在跑。

## 6.2 我们和真实 vLLM 的差别：gather vs 直接读块

诚实交代一下：我们的实现和真实 vLLM 有一个重要差别。

**我们的做法（正确性优先）：** 算注意力前，用 `gather` / `gather_padded` 把散在块里的 K/V **复制**出来，拼成连续张量，再走 Week 2 写的普通注意力。

**真实 vLLM 的做法（性能优先）：** 根本不复制。它有一个专门的 **PagedAttention kernel**（用 CUDA/Triton 手写的 GPU 程序），算注意力时**按块表直接去各个块里读数据**，边读边算——存储是散的，计算直接吃散的，中间没有任何"拼成连续"的步骤。

在真实 vLLM 仓库里，你能看到这对搭档（以 FlashAttention 后端为例，`vllm/v1/attention/backends/flash_attn.py`）：

- **`reshape_and_cache`**：写入侧。每步算出的 K/V 按 `slot_mapping` 原地写进分页 cache——就是我们的 `write`；
- **`flash_attn_with_kvcache`**（或类似变长注意力接口）：读取侧。把块表交给 kernel，kernel 自己翻块表、跳块读数据算注意力——把我们的 `gather` + 注意力**融合**成了一步。

为什么我们教学版选择 gather？三个理由：

1. **你已经能完全看懂。** gather 回来就是 Week 2 的注意力，零新魔法；kernel 的代码需要 CUDA 背景，超出本课程范围；
2. **结果一字不差。** 第 5 章的对拍证明了：gather 方案和朴素方案数学等价。真实 kernel 追求的也是这个等价，只是更快；
3. **概念完全一样。** "块表翻译 + 按块寻址"这个核心思想，两边一字不差。你看懂了我们这版，再读 vLLM 源码时，要补的只是"哦，它把 gather 和注意力融进了一个 kernel"。

一句话：**真实 vLLM 快在 kernel，妙在分页；我们学到了"妙"，没追"快"。**

## 6.3 唯一的旋钮：块大小

分页方案里唯一的超参数是 `block_size`（一块装几个 token）。它两头牵扯：

| 块大小调大 | 块大小调小 |
|---|---|
| 块表更短，翻表开销小 | 块表更长，管理开销大 |
| **内部碎片变大**：最后一个块装不满，平均浪费半个块/请求 | 内部碎片小：最多浪费不到一个小块 |
| 小请求尴尬：提示词只有 3 个 token，也要独占一整块 | 小请求也能精打细算 |

真实 vLLM 默认 `block_size = 16`——在"翻表开销"和"尾块浪费"之间的一个甜点位。我们的教学默认值也是 16（`LLMEngine` 的默认参数，Week 7 见），本周测试里用 2、3、4 这样的小块，纯粹是为了**让小例子也能触发跨块**，方便验证。

> 💡 **你可能会问：块大小会影响生成结果吗？**
>
> 完全不会——第 5 章的选做练习已经让你亲手验证过了：块大小 4 改成 2 或 7，对拍照样绿。块大小是纯粹的**存储参数**，只影响空间利用率和管理开销，不碰数学。这正是"存储与计算解耦"的美妙之处。

## 6.4 没有分页，就没有 Week 5

下周我们要做 continuous batching：请求**随时来、随时走**，不等别人，谁先说完谁先离场。停下来想想，这个"随时"对内存意味着什么：

- 新请求随时进来 → 得**立刻**给它找地方放提示词的 K/V；
- 老请求随时结束 → 它的内存得**立刻**能给别人用；
- 每个请求每步长一个 token → 每个人的"地盘"都在**不停变大**。

连续分配在这三件事面前全军覆没：来了找不到连号空间、走了留下洞、长着长着顶到别人。而分页世界里，这三件事全是家常便饭：**来就领块、走就还块、长就再领一块**——`BlockPool.allocate` / `BlockTable.append_slot` / `BlockTable.free`，你本周写的每一行代码，都是下周调度器的子弹。

再预告一步：下周的 `Scheduler` 会拿着 `pool.can_fit(...)` 做"保守准入"——块池装不下"提示词 + 全部待生成"，新请求就先在等待队列里坐着。你会看到 `can_fit` 和 `needed_blocks` 这两个本周"已经给好"的方法，在调度器里挑大梁。

## 6.5 本周全景回顾

| 零件 | 一句话 | 对标 vLLM |
|---|---|---|
| `BlockPool` | 空闲块队列，发块收块 | `vllm/v1/core/block_pool.py` |
| `BlockTable` | 一个请求的页表：逻辑位置 → 物理槽位 | `vllm/v1/core/kv_cache_manager.py` |
| `PagedKVCache` | 全局分页仓库，`write`/`gather` 按槽位存取 | `reshape_and_cache` + PagedAttention kernel（`vllm/v1/attention/backends/`） |
| `prefill` / `decode_batch` | 模型的引擎接口，认 slot_mapping 和块表两张通行证 | 模型前向 + attention metadata（`vllm/v1/worker/`） |
| 对拍测试 | 换存储不换结果的铁证 | vLLM 自己的正确性测试也是同款思路 |

> 📌 **对标 vLLM：** 至此你已经认识了 vLLM 的心脏地带。块池、页表、按槽位写 cache、按块表做注意力——打开真实仓库 `$VLLM_SRC`，`vllm/v1/core/block_pool.py` 只有两百来行，现在去读，每一行你都讲得出在干嘛。Week 8 我们会正式带读源码，但你已经可以提前去探营了。

> 📌 **划重点：** PagedAttention 省的是 KV cache 的三种浪费，换来的是显存里更高的并发、更高的吞吐、更低的单用户成本。我们用 gather 换正确性，真实 vLLM 用 kernel 换性能，思想是同一个。而分页真正的威力下周才释放——continuous batching 的每一次"随时来、随时走"，踩的都是本周铺的地基。
