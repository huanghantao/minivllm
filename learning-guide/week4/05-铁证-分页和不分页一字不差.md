## 5.1 为什么需要一条"铁证"

回顾我们这一周干了什么：把 KV cache 的存储方式**彻底换掉**了——从"每请求一段连续张量"换成"全局分页仓库 + 块表翻译"。模型的注意力路径也从 `forward` 换成了 `prefill` / `decode_batch`。

这么大的改动，有一个原则必须守住：

> **换存储方式，绝不能换计算结果。**

K/V 存成连续的还是散在块里，只是"放在哪"的区别；"算出什么"必须分毫不动。如果分页版生成的词和老版不一样，那一定是我们哪里写错了——散不散落，不该影响数学。

怎么验证？**对拍**：同一个模型、同一个提示词、同样的贪心解码，老路（Week 3 的 `generate_with_cache`）走一遍，新路（分页接口）走一遍，**生成的 token 序列必须一字不差**。这就是 `test_paged_equals_naive` 干的事。

## 5.2 手工扮演调度层：paged_generate_single

测试文件里有个辅助函数 `paged_generate_single`，它是 Week 5 调度器的"袖珍手工版"——调度层该干的活（占座、记账、传通行证），这里用最直白的代码全做了一遍：

```python
def paged_generate_single(model, prompt_ids, max_new_tokens, pool, kv_cache):
    """用分页接口做贪心生成（单请求），返回生成的 token id 列表。"""
    bt = table_mod.BlockTable(pool)
    slots = [bt.append_slot() for _ in prompt_ids]
    ids = torch.tensor(prompt_ids, dtype=torch.long)
    logits = model.prefill(ids, kv_cache, slots, bt)
    out = [int(torch.argmax(logits).item())]
    for _ in range(max_new_tokens - 1):
        slot = bt.append_slot()
        token = torch.tensor([out[-1]], dtype=torch.long)
        pos = torch.tensor([bt.num_tokens - 1], dtype=torch.long)
        logits = model.decode_batch(token, pos, kv_cache, [slot], [bt])[0]
        out.append(int(torch.argmax(logits).item()))
    return out
```

逐段拆解：

**① prefill 前的占座。**

```python
bt = table_mod.BlockTable(pool)
slots = [bt.append_slot() for _ in prompt_ids]
```

给这个请求建一张块表，提示词有几个 token 就占几个槽位——这就是第 2 章的 `append_slot`，块满了自动领新块。`slots` 就是 prefill 要的 `slot_mapping`："这 L 个 token 分别写进哪些槽位"。

**② prefill + 第一个词。**

```python
logits = model.prefill(ids, kv_cache, slots, bt)
out = [int(torch.argmax(logits).item())]
```

`prefill` 返回最后位置的 logits `(vocab,)`，`argmax` 取分数最高的词——贪心解码（Week 1 就用的它）。注意传给模型的四样东西：`ids`（算什么）、`kv_cache`（写到哪个仓库）、`slots`（写去哪）、`bt`（从哪读历史）。

**③ decode 循环：每步先占座，再算。**

```python
slot = bt.append_slot()
token = torch.tensor([out[-1]], dtype=torch.long)
pos = torch.tensor([bt.num_tokens - 1], dtype=torch.long)
logits = model.decode_batch(token, pos, kv_cache, [slot], [bt])[0]
```

每生成一个新 token：

1. **先 `append_slot()` 占一个座**——新 token 的 K/V 马上就要写进这个槽位；
2. `token`：上一步生成的词，是本步的输入。包成 `(1,)` 的张量——`decode_batch` 是批量接口，**单请求就是 B=1 的批**；
3. `pos`：新 token 的位置编号。刚占完座，`bt.num_tokens` 已经自增过了，所以这个 token 是第 `bt.num_tokens - 1` 个（从 0 数起）；
4. `decode_batch(token, pos, kv_cache, [slot], [bt])` 返回 `(1, vocab)`，取 `[0]` 得到这个请求的 logits。

⚠️ 这段代码里藏着本周最好的一个"自检点"：`pos` 和 `slot` 必须描述**同一个 token**。如果你把 `append_slot()` 挪到 `decode_batch` 之后调用，位置编号就会差 1，生成的词立刻变样——对拍测试会毫不留情地红给你看。

## 5.3 主测试：新老两条路，终点必须相同

```python
def test_paged_equals_naive(mini_model):
    """换存储方式绝不能换结果：分页生成的词和 Week 3 的一模一样。"""
    prompt = [3, 1, 4]
    n = 6
    cached = generate_mod.generate_with_cache(
        mini_model, torch.tensor([prompt]), max_new_tokens=n
    )
    expected = cached[0, len(prompt):].tolist()

    pool = pool_mod.BlockPool(num_blocks=8, block_size=4)
    C = mini_model.config
    kv_cache = paged_mod.PagedKVCache(
        C.num_layers, C.num_heads, C.head_dim, num_blocks=8, block_size=4
    )
    got = paged_generate_single(mini_model, prompt, n, pool, kv_cache)
    assert got == expected
```

（`mini_model` 是测试框架准备好的一个小 `MiniTransformer`，权重固定，保证每次跑结果可复现。）

四步走：

1. **老路打样**：`generate_with_cache`（Week 3 的作品，`NaiveKVCache` 那套）从提示词 `[3, 1, 4]` 贪心生成 6 个新 token，切掉提示词部分，得到 `expected`；
2. **搭分页舞台**：8 个块、每块 4 个 token 的池子；`PagedKVCache` 的层数、头数、头维度**直接从模型配置里取**（`C.num_layers, C.num_heads, C.head_dim`）——仓库的尺寸必须和模型严丝合缝，否则 `write` 时形状对不上；
3. **新路生成**：`paged_generate_single` 走一遍，得 `got`；
4. **一字不差**：`assert got == expected`——不是"差不多"、不是"误差小于多少"，是 token id **完全相等**。

为什么敢要求完全相等？因为两条路用的是**同一个模型、同一套权重、同样的贪心规则**，分页只做存储层的搬运：写进去的是什么，gather 回来的就是什么（第 3 章的 roundtrip 测试已经钉死了这一点）。数学上两条路等价，实现正确就必须**逐位相同**。

这条测试还是本周所有零件的**总装检验**：`BlockPool`、`BlockTable`、`PagedKVCache`、模型的两个新接口，任何一个有 bug，`got` 都会对不上 `expected`。

```bash

```

11 条测试全绿（4 条块池 + 3 条块表 + 3 条分页仓库 + 1 条对拍），Week 4 的核心就到手了。

> 💡 **你可能会问：对拍只测了 6 个 token、3 个提示词，够吗？**
>
> 对教学来说够了：块大小 4、提示词 3 个 token——**生成第 2 个新 token 时就会触发"领第二块"**（3 + 2 > 4），跨块读写、槽位公式、gather 顺序全被考验到了。小例子覆盖关键路径，是测试设计的理想状态。真实项目里还会加随机提示词、多块、多请求的对拍，思想完全一样。

> ⚠️ **易踩坑：** 如果这条测试红了，**先别怀疑数学**，按依赖顺序自底向上排查：`pytest tests/test_w4.py -k "pool or block_table"` 绿了吗？`-k paged`（仓库三条）绿了吗？前两层绿了才对拍不绿，那问题几乎一定在第 4 章的形状变换（`view`/`permute`/mask）里。

> 📌 **划重点：** `test_paged_equals_naive` 是本周的验收标准：同一模型、同一提示词、同样贪心，分页版和 Week 3 老路生成的 token 必须一字不差。存储怎么折腾是自由，吐出什么词是纪律。
